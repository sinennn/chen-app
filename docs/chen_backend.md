**CHEN**

Backend Architecture Document

_v1.0 - MVP_

Built by Sy | Stack: Golang + Gin · Supabase · PostgreSQL

# **1\. Overview**

Chen is a social music application that allows users to see what their friends are listening to in real time across Spotify, Apple Music, and Audiomack. The backend is the central nervous system of the app - it handles authentication, music platform integrations, real-time data flow, AI (Chen the assistant), payments, and push notifications.

The backend is built with Golang using the Gin framework, backed by Supabase (PostgreSQL) for data persistence and real-time subscriptions. It is designed to be modular, scalable, and AI-codeable - each internal module is self-contained with its own routes, handlers, and service logic.

# **5\. Module Breakdown**

## **5.1 auth/**

Handles JWT validation middleware for all protected routes. Every request to the Gin server that requires authentication passes through this middleware. It validates the Supabase JWT token from the Authorization header and attaches the user ID to the request context for downstream handlers.

- Middleware: ValidateJWT - extracts and verifies Supabase JWT
- Helper: GetUserFromContext - retrieves authenticated user ID from Gin context

## **5.2 spotify/**

The most complex module. Manages the full Spotify OAuth 2.0 flow and a background polling service that detects currently playing tracks for all connected users every 30 seconds.

- GET /api/v1/auth/spotify - redirects user to Spotify OAuth consent screen
- GET /api/v1/auth/spotify/callback - exchanges auth code for tokens, stores encrypted in Supabase
- Token refresh middleware - automatically refreshes expired access tokens before every Spotify API call (tokens expire every 60 minutes)
- Polling service - goroutine that runs every 30 seconds, calls /me/player/currently-playing for each connected user, writes new tracks to listening_activity

## **5.3 applemusic/**

Handles Apple Music integration using MusicKit. Generates signed JWT developer tokens from your .p8 private key and Team ID. Polls currently playing data for connected Apple Music users.

- JWT generation - signs developer token using ES256 with your Apple private key
- GET /api/v1/auth/applemusic - initiates Apple Music user authorization
- GET /api/v1/auth/applemusic/callback - stores music user token
- Polling service - same 30-second pattern as Spotify

## **5.4 audiomack/**

Audiomack integration. Pending API key approval. Architecture mirrors Spotify module. Will be activated once Audiomack responds to the partnership request.

- OAuth flow for Audiomack account connection
- Polling service for currently playing detection (subject to API capabilities)

## **5.5 friends/**

Manages the social graph. Uses the friendships table with a status field to track pending, accepted, and blocked relationships.

- POST /api/v1/friends/request - send a friend request
- POST /api/v1/friends/accept - accept a pending request
- POST /api/v1/friends/decline - decline a request
- POST /api/v1/friends/block - block a user
- GET /api/v1/friends - list all accepted friends with their current listening status

## **5.6 activity/**

Serves the friend activity feed. The real-time magic actually happens on the client via Supabase Realtime subscriptions - this module handles REST fallbacks and historical activity queries.

- GET /api/v1/activity/feed - paginated historical activity for friend feed
- GET /api/v1/activity/user/:id - specific user's listening history

## **5.7 compatibility/**

Calculates music compatibility scores between friend pairs. Runs as a background job once daily rather than on every request - this keeps response times fast and prevents hammering the database.

- Background job - recalculates all friendship compatibility scores nightly
- Algorithm v1 - shared artist percentage weighted by listening frequency
- GET /api/v1/compatibility/:friend_id - retrieve score between authenticated user and a friend
- Future: mood overlap, genre alignment, listening time correlation

## **5.8 chen/**

The AI assistant module. Handles all communication between the app, Groq's API, and conversation memory stored in Supabase. Chen's intelligence comes from a carefully crafted system prompt that is injected with real-time context about what the user and their friends are listening to.

- POST /api/v1/chen/message - receives user message, builds context, calls Groq, returns response
- GET /api/v1/chen/history - retrieves conversation history for the current user
- Context injection - before every Groq call, Gin fetches: current user track, friends' current tracks, user's top artists from history, compatibility scores. This context is prepended to Chen's system prompt.
- Rate limiting - free tier users limited to 10 messages/day, premium users unlimited
- Model: llama3-70b-8192 via Groq for fast, high quality responses

## **5.9 payments/**

Handles Paystack subscription billing. Listens for Paystack webhook events to update user premium status in real time.

- POST /api/v1/payments/initialize - creates a Paystack payment session for subscription
- POST /api/v1/payments/webhook - receives Paystack events (charge.success, subscription.disable)
- Webhook handler updates is_premium on the users table based on subscription status
- GET /api/v1/payments/status - returns current subscription status for authenticated user

## **5.10 notifications/**

Triggers push notifications via Expo's push notification service. Called internally by other modules when notification-worthy events occur.

- Notify when a friend starts listening to something
- Notify when a new friend request is received
- Notify when compatibility score updates
- Uses Expo's push token stored on the user record

# **6\. Real-Time Architecture**

The real-time friend feed works through a chain of three systems working together. Understanding this flow is critical.

- Step 1 - Gin's polling service runs every 30 seconds in a goroutine, calling Spotify/Apple Music/Audiomack APIs for each connected user
- Step 2 - When a new track is detected, Gin writes a new row to the listening_activity table in Supabase
- Step 3 - Supabase Realtime detects the new row and broadcasts it to all active subscribers
- Step 4 - The React Native client has a Supabase Realtime subscription open, filtered to only receive activity from the authenticated user's friends
- Step 5 - The client updates the feed UI instantly without polling

This architecture means the client never polls - it just listens. All the heavy lifting is done server-side. Supabase RLS policies ensure users can only subscribe to activity from accepted friends, never strangers.

# **7\. Chen AI Request Flow**

Every time a user sends Chen a message, the following sequence runs inside the chen/ module:

- 1\. Request arrives at POST /api/v1/chen/message with the user's message text
- 2\. Auth middleware validates JWT and extracts user ID
- 3\. Context builder fetches from Supabase: user's currently playing track, friends' currently playing tracks, user's top 10 artists from last 30 days, compatibility scores with friends
- 4\. System prompt is assembled: Chen's personality + injected context
- 5\. Conversation history is loaded from chen_conversations (last 20 messages for memory)
- 6\. Full payload is sent to Groq API (model: llama3-70b-8192)
- 7\. Groq streams back the response
- 8\. Response is saved to chen_conversations in Supabase
- 9\. Response is returned to the client

The streaming step (7) is important for perceived speed. Rather than waiting for the full response before sending anything, Gin streams Groq's output token-by-token to the React Native client. Users see Chen's response appearing in real time, which makes her feel fast and alive.

# **9\. Recommended Build Order**

Build in this order to avoid dependency hell. Each phase unlocks the next.

- Phase 1 (Days 1-3): Gin server bootstrap, Supabase schema creation, auth middleware, basic health endpoint
- Phase 2 (Days 4-7): Spotify OAuth + token management + polling service + listening_activity writes
- Phase 3 (Days 8-10): Apple Music integration, Audiomack (if keys arrived), friend system
- Phase 4 (Days 11-13): React Native UI - ethereal design system, real-time feed, themes
- Phase 5 (Days 14-16): Chen AI module - Groq integration, context injection, conversation memory
- Phase 6 (Days 17-18): Compatibility scores, Paystack subscriptions, push notifications
- Phase 7 (Days 19-20): End-to-end testing, bug fixes, performance polish, deploy

# **10\. Security Notes**

- RLS enabled on all Supabase tables - users can only read their own data and accepted friends' activity
- Spotify and Apple Music tokens are encrypted at rest in Supabase - never stored in plaintext
- Groq, Paystack, and Apple Music private keys live in Gin only - never exposed to the React Native client
- Paystack webhooks are verified using HMAC signature validation before processing
- .env is gitignored - regenerate all keys if accidentally exposed
- Rate limiting on Chen messages per user tier to prevent API abuse
